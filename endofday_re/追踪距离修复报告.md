# 僵尸追踪距离修复报告

## 📋 问题描述

**现象**：虽然配置文件中设置了僵尸的追踪距离（FOLLOW_RANGE）为 128 格，但实际游戏中僵尸的追踪距离仍然只有原版的 16 格左右，无法远距离发现并追踪玩家。

**影响范围**：所有使用自定义属性的怪物实体，特别是僵尸类生物。

---

## 🔍 问题分析

### 1. 配置检查
在 `AttributeBuild.java` 第 25 行，追踪距离已正确配置：
```java
Map.entry("追踪距离", new AttributeData(
    ModUtils.getAttributeId(Attributes.FOLLOW_RANGE.value()),
    "minecraft:zombie",
    "endofdays_re.attribute.follow",
    "128",  // ✅ 配置值正确
    1, 100, 1024.0f
))
```

### 2. 代码执行流程分析

#### ❌ 修复前的执行顺序：
```
1. EntityGoalRegisterEvent 触发
   └─> GoalHelper.initGoal() 创建 AI 目标
       └─> NearestAttackTargetGoal 读取 FOLLOW_RANGE 属性
           └─> 此时属性尚未应用，读取到原版默认值 16 格
   
2. 后续属性更新（每 60 tick 或生成时）
   └─> AttributeHelper.attribute()
       └─> 设置 FOLLOW_RANGE = 128 格
           └─> ❌ 但 AI 目标已经创建完成，不会重新读取
```

#### 关键代码位置：
- **ServerForgeEvent.java 第 407-413 行**：`onEntityGoalRegister()` - 创建 AI 目标
- **ServerForgeEvent.java 第 318、430 行**：`AttributeHelper.attribute()` - 应用属性
- **GoalHelper.java 第 36-39 行**：读取追踪距离创建 AI

```java
// GoalHelper.java 第 36-39 行
AttributeInstance follow_attribute = mob.getAttribute(Attributes.FOLLOW_RANGE);
if (follow_attribute != null) {
    // ⚠️ 这里读取的是当前属性值，如果属性还没应用，就是默认值
    goal.addGoal(8, new NearestAttackTargetGoal<>(
        mob, LivingEntity.class, false, 
        follow_attribute.getValue(),  // ← 问题点：读取时机错误
        follow_attribute.getValue(), 
        commonConfigData.Target.values().stream().toList()
    ));
}
```

### 3. 根本原因
**事件调用顺序错误**：AI 目标的创建发生在属性应用之前，导致 AI 系统使用了错误的初始值。

---

## 🛠️ 修复方案

### 修改文件：`ServerForgeEvent.java`

**修改位置**：第 407-413 行 `onEntityGoalRegister()` 方法

**修改内容**：
```java
@SubscribeEvent
public static void onEntityGoalRegister(EntityGoalRegisterEvent event) {
    if (event.livingEntity instanceof Monster pathfinderMob && !event.livingEntity.level().isClientSide()) {
        // ✅ 新增：先应用属性（包括追踪距离 128 格）
        AttributeHelper.attribute(pathfinderMob);
        
        if (event.goalSelector != null) {
            // 再创建 AI 目标，此时能读取到正确的属性值
            GoalHelper.initGoal(event.goalSelector, pathfinderMob);
        }
    }
}
```

### 修复后的执行顺序：
```
1. EntityGoalRegisterEvent 触发
   └─> AttributeHelper.attribute() 先应用属性
       └─> 设置 FOLLOW_RANGE = 128 格 ✅
   
2. GoalHelper.initGoal() 创建 AI 目标
   └─> NearestAttackTargetGoal 读取 FOLLOW_RANGE 属性
       └─> 读取到已更新的值 128 格 ✅
```

## 🔧 附加修复

在修复追踪距离问题时，同时优化了以下相关问题：

### 1. 僵尸死亡回血问题
**问题**：僵尸被杀死后瞬间回到 1 点血，处于"假死"状态  
**原因**：`AttributeHelper` 中的血量保底逻辑 `Math.max(1.0f, ...)`  
**修复**：添加死亡检查 `!livingEntity.isDeadOrDying()`

```java
// AttributeHelper.java 第 51 行
if (maxHealthAttr != null && !livingEntity.isDeadOrDying()) {
    // 只有存活的实体才调整血量
    double newMaxHealth = maxHealthAttr.getValue();
    float newHealth = (float) (newMaxHealth * healthRatio);
    newHealth = Math.max(1.0f, Math.min(newHealth, (float) newMaxHealth));
    livingEntity.setHealth(newHealth);
}
```

### 2. 血量比例保持
**优化**：属性更新时保持当前血量比例，避免受伤后回满血  
**实现**：记录 `healthRatio = currentHealth / maxHealth`，更新后按比例调整

## 📝 总结

### 问题本质
这是一个典型的**初始化顺序问题**（Initialization Order Problem），在面向对象编程和事件驱动系统中非常常见。

### 解决思路
1. **识别依赖关系**：AI 目标依赖属性值
2. **调整执行顺序**：确保依赖项先于使用者初始化
3. **防御性编程**：添加状态检查（如死亡检查）避免边界情况

### 经验教训
- ✅ 在事件驱动的系统中，事件触发顺序至关重要
- ✅ 属性系统应在 AI 系统之前初始化
- ✅ 对于动态更新的属性，需要考虑更新时机对已创建对象的影响
- ✅ 添加适当的日志和调试信息有助于快速定位此类问题
